# research/wiki/raw/

Immutable source materials. The archive layer that feeds `research/wiki/`.

## Mental model

```
research/wiki/raw/   → immutable inputs (papers, scrapes, dataset notes)
research/wiki/       → distilled, queryable pages (built from raw/)
```

A claim in a wiki page always cites a source page; a source page always
cites a file under `research/wiki/raw/`. The chain back to evidence is unbroken.

## Rules

1. **Never edit a file in `research/wiki/raw/`.** Once written, it stays. If a source is
   wrong, note the correction in the corresponding `research/wiki/` page — not here.
2. **Always preserve.** Do not delete from `research/wiki/raw/` even if a source seems
   superseded. The full audit trail is part of the value.
3. **Name with a date prefix.** Format: `YYYY-MM-DD_<slug>.<ext>`. The date
   is the day the source was acquired (downloaded, scraped, transcribed),
   not the publication date — publication date belongs in the corresponding
   `research/wiki/sources/<slug>.md` page's frontmatter.

## What counts as raw

- PDFs of papers, books, reports (non-copyrighted; copyrighted papers go in
  the top-level `literature/`, which is gitignored).
- Scraped articles (full HTML, or markdown-converted-from-HTML).
- Dataset codebooks, README files shipped with downloads.
- Transcripts (interviews, meetings, podcasts).
- Photographs of physical documents.
- Screenshots of dashboards or tables that can't be exported.

If it came from outside the project and you'd want to point at it later as
evidence, it goes here.

## What does NOT count

- Anything *generated by the project* (charts, panel CSVs, regression
  outputs). Those belong in `output/` and are governed by the
  `script-header` and `analytical-commit-format` conventions.
- Personal notes — those are scratch, not sources.
- Drafts of project deliverables — those go in `deliverables/`.
- Copyrighted PDFs you can't redistribute — those go in top-level
  `literature/` (gitignored).

## Layout

```
research/wiki/raw/
├── README.md          (this file)
├── registry.yaml      ← scrape watchlist (curated by hand)
├── seen.jsonl         ← dedup ledger (maintained by /scan-sources)
├── scraped/           ← tracked-source content (one subdir per slug)
│   └── <slug>/
│       └── YYYY-MM-DD_<title-slug>.md
└── <loose files>      ← one-off acquisitions (papers, codebooks, transcripts)
```

Two layouts coexist under `research/wiki/raw/`:

- **Loose files at the root** — `research/wiki/raw/YYYY-MM-DD_<slug>.<ext>`. Use for
  one-off acquisitions: a paper a colleague forwarded, a dataset
  codebook, an ad-hoc scrape from the `web-scraping` skill, a meeting
  transcript. No registry entry, no recurring fetch.

- **Continuous-scrape subtrees** — `research/wiki/raw/scraped/<slug>/YYYY-MM-DD_<title-slug>.md`.
  Use for sources tracked in `research/wiki/raw/registry.yaml` and fetched by
  `/scan-sources`. The skill creates the per-slug directory on first
  fetch; one file per fetched item; YAML frontmatter carries `url`,
  `source_slug`, `category`, `scraped_at`, `content_sha256`, `title`.

The `scraped/<slug>/` layout is reserved for `/scan-sources` output. Don't
drop loose files into a slug directory; if a one-off acquisition relates
to a tracked source, put it at the `research/wiki/raw/` root and note the
relationship in the wiki page.

## The scrape registry

`registry.yaml` is the project's curated watchlist of URLs to re-scrape
periodically. `/scan-sources` reads it, fetches what's due, dedupes
against `seen.jsonl`, and lands new content under `scraped/<slug>/`.

### How to register a new source

1. Decide the slug. Short, kebab-case, unique within the registry.
   Used as the directory name under `scraped/`. Examples:
   `cambodia-mef-news`, `vn-port-throughput`, `kh-exchange-filings`.
2. Pick the category from the closed list:
   `investment | company | innovation | infrastructure | policy | news | other`.
3. Pick the freq from the closed list:
   `daily | weekly | monthly | adhoc`.
   Use `adhoc` for sources you never want auto-scraped — they fire
   only under `--slug` or `--force`.
4. Pick the scrape method by escalation:
   - Try `httpx` first (cheap, fast, works for most static HTML).
   - Move to `playwright` if the page is JS-rendered or behind a login.
   - Move to `crawl4ai` for content-heavy prose pages where you want
     clean markdown.
   - Move to `scrapegraph` (LLM-driven) only when structure is
     irregular and selectors won't hold. Pricey — use sparingly.
5. (Optional) Add a `content_selector` — a CSS selector or XPath that
   narrows the page to its meaningful body. Skipping this means the
   skill will scrape the full page including nav and footer, which
   inflates the content hash and hurts dedup quality.
6. Write a `notes` field. One or two lines: why this source is worth
   tracking, what to watch for, what's known to break.
7. Set `last_scraped: null`. The skill will populate it on first run.

Append the entry to the `sources:` list in `registry.yaml`. Commit with a
message that explains the addition (the rationale belongs in git log too,
not just in `notes`).

### How to retire a source

Don't delete the entry — set `freq: adhoc` and add a `notes` line
explaining when/why you stopped tracking it. This preserves the audit
trail. Old `scraped/<slug>/` files stay (raw is immutable). If the source
becomes interesting again, flip the freq back.

### How to force a re-fetch

```
/scan-sources --slug=<slug> --force
```

Use this when:
- A registry entry's last fetch failed or returned bad content.
- A breaking event happened and you need fresh content before the freq
  window opens.
- You changed the `content_selector` and want to re-extract from the
  same URL.

`--force` bypasses the freq check but **not** the dedup check. If the
re-fetched content has the same sha256 as the prior fetch, no new file is
written.

### How to query past scrapes

`seen.jsonl` is the dedup ledger of successful fresh content. With `jq`
installed:

```bash
# All distinct content sha256s captured for one source
jq 'select(.slug == "investment-news-cambodia")' research/wiki/raw/seen.jsonl

# All fresh content captured in the last 30 days
jq --arg cutoff "$(date -u -v-30d +%Y-%m-%dT%H:%M:%SZ)" \
   'select(.scraped_at > $cutoff)' research/wiki/raw/seen.jsonl

# Distinct URLs ever seen for a slug (useful when the index URL changes)
jq -r 'select(.slug == "policy-news-example") | .url' research/wiki/raw/seen.jsonl | sort -u
```

For run history (including failures and duplicates), use git instead:

```bash
# When did we last update last_scraped for this entry?
git log -p -- research/wiki/raw/registry.yaml | grep -B1 'investment-news-cambodia'

# Every fresh-content commit
git log -- research/wiki/raw/scraped/

# Per-run failures: scan the per-run reports in your shell history,
# or grep recent commits for "scan-sources" mentions.
```

## Ingest into the wiki

`research/wiki/raw/` is the archive; `research/wiki/{sources,concepts,entities,synthesis}/`
is the queryable layer. To bring a raw file into the wiki, run:

```
/wiki-ingest research/wiki/raw/<filename>
```

See `research/wiki/README.md` and `research/wiki/SCHEMA.md` for what ingest produces.

## What this directory is NOT

- **Not a bookmarks file.** Free-form URL lists go in your notes app.
  `registry.yaml` is structured input to `/scan-sources`.
- **Not a crawl seed list.** One URL per registry entry. Multi-page
  indexes need multiple entries.
- **Not the wiki.** Scraped content lands here in `scraped/`; promotion
  to load-bearing knowledge requires explicit `/wiki-ingest`.
